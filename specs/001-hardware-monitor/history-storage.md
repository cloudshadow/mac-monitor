# 低负载持久历史设计

日期：2026-10-01。用户确认整机30天、应用摘要7天。所有资源数字为待验证预算。

## 核心决策

Swift Agent 内嵌 SQLite，实时采样留在有界内存里，每60秒提交一次系统历史；应用先在内存累积5分钟，再把最终排行摘要加入下次事务。一个历史连接和专用串行队列复用预编译语句；网络与采集线程不等待数据库查询。不启动数据库服务，不要求用户安装 SQLite。

```mermaid
flowchart LR
    C[原生采样] --> M[内存快照与时间桶]
    M --> W[60秒批量提交]
    W --> D[本地 SQLite]
    D --> Q[有界历史查询]
    Q --> UI[React 网页]
    M --> UI
```

## 采样频率和保存精度

| 数据 | 采样 | 持久精度 | 保留 |
| --- | --- | --- | --- |
| 整机CPU/内存/系统I/O | 持续1s，不依赖查看者 | 1分钟 | 24小时 |
| 温度 | 持续10s，电源/异常显式降频 | 同系统桶，保存观测极值 | 同系统历史 |
| 系统中期历史 | 由1分钟桶汇总 | 5分钟 | 7天 |
| 系统长期历史 | 由5分钟桶汇总 | 1小时 | 30天 |
| 应用排行摘要 | 持续4s，不依赖查看者 | 5分钟 | 7天 |

三种系统精度在物理存储上重叠保留；UI自动按时间段/图表宽度选择，跨层交界不重复计数。单个连续segment、时间窗口对齐时，分钟桶数1440、5分钟桶2016、小时桶720；64条序列的名义估算为267,264行。这不是全库行数上限：窗口边缘部分桶、重启、唤醒和时钟跳变会增加segment及同一墙钟桶的行数，实际容量由下文磁盘预算约束。近期内存系统最多360个1秒槽/序列，应用最多90帧且每帧30组，共享近期缓冲字节硬上限4MiB；逻辑保留最近五分钟及至多一分钟衔接余量。重启只恢复持久聚合精度。内存与数据库可同时持有近期数据，仍每60秒落盘，无需等五分钟；查询分界、覆盖与去重详见 [realtime-data-flow.md](realtime-data-flow.md)。

应用每5分钟从所有成功观测的应用中，取时间加权CPU均值Top10、观测内存最大值Top10、磁盘读写合计增量Top10的并集，最多30组。不是每次采样各取Top30再累积；否则会突破上限。单个连续segment、窗口对齐时，7天名义估算60,480条应用桶；多个segment的部分窗口会增加行数，不能作为全库硬上限。磁盘合计仅用于选榜，读和写分别存储。

应用字典与未完成桶合计上限4,096个身份；超限时记录覆盖降低，淘汰策略不得把缺失标为零。稳定bundle身份跨服务重启保留；未归属进程沿用进程启动身份，过期无引用后清理。历史只保存显示名/本地身份散列和指标，不保存命令行、完整路径、窗口标题或访问网址。

每桶记录 `min/max/weightedSum/coveredDurationMs/sampleCount`；平均值用有效时长加权，不能平均不同覆盖的平均数。应用CPU按连续两次可读采样间隔计算，内存为观测值，瞬时峰值和短命进程可能漏采。低频扫描不代表完整活动审计；未入榜显示“未保留”，不得显示0。

## SQLite 参数与线程

- 使用与应用一同编译的 SQLite C 库，锁定经验证的维护版本；至少包含官方 WAL-reset 修复（3.51.3+或官方回补版）。运行时报告实际版本，第三方许可随包提供。
- 历史库 `history.sqlite`：WAL、`synchronous=FULL`、macOS评估启用`fullfsync=ON`、`foreign_keys=ON`；不使用`OFF`。当前设计接受每分钟一次批量持久事务的成本，实际同步次数还包括检查点等操作。
- `cache_size=-2048`（2MiB目标）、`mmap_size=0`、短`busy_timeout`；有界写入队列≤2MiB。按数据库页/语句测量实际内存，缓存参数不是进程总内存上限。
- 关闭默认自动检查点，写入队列在WAL达到约4MiB或累计5分钟后运行PASSIVE检查点。单连接串行读写/检查点，查询必须在预算内结束；无长读事务。WAL超过8MiB时先让查询退出并推进检查点，持续失败暂停历史写入并显示状态。
- 账号/配置使用独立`state.sqlite`，低频写入且FULL同步；不会每分钟重写密码/设置。两个数据库不要求跨库事务，清空或隔离历史不影响账号。
- 不在采集/HTTP event loop中执行SQLite，不为每个网页创建连接。不采用周期`VACUUM`；按小时分批回收过期记录并复用空闲页，显式清理时才评估压缩。

[SQLite WAL](https://sqlite.org/wal.html)、[同步模式与fullfsync](https://sqlite.org/pragma.html#pragma_synchronous)。FULL有助于正常系统/文件系统保证范围内的事务持久性，不能保证磁盘物理故障零损失。NORMAL在断电后可能回滚已提交事务，不能简单宣传为“只丢60秒”。

## 聚合、崩溃与时间

系统分钟桶和相应5分钟/小时累计结果在同一事务写入，使用唯一桶键和基于源桶的幂等重算，避免重试翻倍。每个分钟结束更新至多一个当前5分钟桶及一个当前小时桶；应用只在5分钟窗口结束提交最终摘要。正常停止尝试限时提交部分桶并标注partial；睡眠通知只作best-effort，不承诺系统一定给足写盘时间。

正常无积压时，进程异常终止可能丢最后未提交约60秒系统记录与未结束约5分钟应用摘要。若系统繁忙、睡眠或写入失败，缺口可能更长，`lastCommittedAt`是可信依据。不能把UI已显示的数据等同于已落盘数据。

桶定位用UTC，计算持续时间与速率用单调时钟。持久`recordingSegmentId`在服务启动、睡眠恢复或时钟显著跳变时新建；唯一键包含segmentId，时钟回拨不会覆盖旧桶。查询遇重叠墙钟区间分段显示，不把两段当作同一段连续时间相加。终止/睡眠/故障区间保留gap。

## 查询与容量

系统查询最多30天、8条序列、每条600点；应用摘要最多7天、每页100组、按窗口分页。用(seriesId,resolution,bucketStart)与(windowStart,appId)范围索引。首版数据库任务按优先级排队，写入优先；查询通过SQLite progress handler在250ms预算内中止并返回可重试状态，服务端整体p95目标500ms。所有参数绑定，API不接受任意SQL。

磁盘目标：历史库、WAL、SHM合计≤256MiB；这是默认运行预算，不是行大小推导出的承诺。达到约240MiB提前清理和检查点，必要时显式缩短实际保留期；高水位仍无法下降则暂停写入。配置数据库`max_page_count`及每事务增长上限，预留WAL空间，发现超限最多容许一个受限事务的暂态增长（≤1MiB）后停止新增历史。不靠删除行立刻缩小文件大小，空闲页优先复用。

存储预估必须计入B-tree页、索引、应用维表、WAL和检查点。物理写入目标≤128MiB/24h，不能用净数据库大小代替写入量；账号操作、日志、安装包下载、人工备份另列。固定命名维表随无引用历史回收，防止长期开新应用后维表无界增长。

正常低电量仍每60秒批量提交，采样降频；发生预算超标先报告并优化，不暗中延长丢失窗口。性能测试必须开启默认历史，包含整点聚合、保留期清理、页面历史查询和24小时运行。原无人查看CPU≤0.2%/40MiB预算保持为待测目标，但持续1秒/4秒已显著增加工作量，须重测并报告是否可达；不得使用旧15秒/60秒配置的结果。

## 文件与故障处理

历史文件放`/Library/Application Support/CloudMacMonitor/data/`，root保护父目录，data目录服务所有者拥有且0700、数据库及旁文件0600，默认不云同步。LaunchDaemon不依赖Mac用户登录即可访问；TLS秘密另放secrets目录，见 [launchdaemon.md](launchdaemon.md)。历史是本地明文数据库，网页密码控制访问而不等于数据库加密；不把认证密码当磁盘加密密钥。

初始化/迁移由程序自动处理。历史损坏时隔离故障库并提示恢复/清空；磁盘满、只读或迁移失败暂停历史模块，实时监测继续。历史清空是本机管理操作；不能影响账号库。复制备份使用SQLite backup API或安全关闭后的完整文件状态，不能只拷贝活动WAL库的主文件。迁移备份限1份，容量另计并在验证成功后清理；磁盘空间不足不启动迁移。

## 查询时合并与点数预算（I1 / I2）

持久层仍只有1m/5m/1h；查询可临时合并成2h、3h等更粗的桶，不新增周期写入。30天完整小时数据为720点，maxPoints=600时可返回约360个2小时桶；不能截掉最早120小时来满足点数限制。

1. 捕获一次查询版本，按既定内存/数据库边界选取不重叠的来源；来源层选择最细可用且在执行预算内的层，层切换只在完整桶边界进行。
2. 以最大来源精度为基数B，候选输出宽度为B的正整数倍；初值不小于 `B * ceil((to-from)/(maxPoints*B))`。按UTC网格对齐，计数后增大宽度，直至每序列全部segment合计不超过maxPoints。边缘桶也计一点，不能只用时长除宽度估计。计算、计数与合并共用250ms执行预算，禁止无界重试或先载入全库。
3. 仅合并同一segment、同一连续覆盖段内的完整来源桶。累加weightedSum、coveredDurationMs和sampleCount，min取最小、max取最大；平均值重新计算。缺失、回拨重叠和不同segment不相加，缺口两侧分别输出并断线。来源桶已有partial覆盖时保留partial，不臆造桶内缺失位置。
4. 如果连续段数量已超过点数预算，再加宽也无解，返回400 `pointBudgetTooSmall`及 `minimumRequiredPoints`（超过600只返回下界601和 `minimumIsLowerBound=true`），引导缩小范围或增加maxPoints。不得静默丢segment。预算耗尽仍返回503 `queryBudgetExceeded`，不伪装空数据。
5. 响应每段报告 `sourceResolutionSeconds / resolutionSeconds / segmentId / continuityId / partial`，顶层resolution相同时为秒数、不同时为mixed；降采样本身不算truncated。范围边缘与来源桶相交时保留整个来源桶并标注其实际起止及partialRange；不按比例猜测半桶的sum/extrema，effectiveRange明确实际覆盖，可在图表裁剪显示。

容量夹具覆盖单segment基线、频繁重启/睡眠、同桶多segment和回拨重叠；检查实际DB/WAL/SHM及维表大小、清理和查询时间，不用名义行数代替磁盘高水位规则。

## 暂停、恢复和清空的串行边界（U5）

`history.sqlite`的单行HistoryControl元数据保存 `recordingEpoch`（递增十进制字符串）、`enabled` 和 `clearedAt`；这是记录开关的唯一持久来源，不在state.sqlite重复保存。HistorySegment元数据将每个recordingSegmentId绑定到epoch，所有持久查询仅可见当前epoch的segment。所有聚合批次及历史查询携带epoch，历史协调器串行处理控制命令、提交和结果发布；采集不等待磁盘。

- **pause**：关闭持久聚合入口，完成边界前已接受的有界批次和部分桶提交，在同一串行流程提交enabled=false；成功后才反馈paused。刷盘失败报告失败/错误及真实提交水位，停止接纳新持久样本，禁止声称已持久保存暂停选择。最近五分钟环形缓冲和实时快照继续更新，界面写明“已暂停保存，近期实时数据仍可查看”。
- **resume**：提交enabled=true后新建recordingSegmentId，从恢复边界之后开始聚合；不回填暂停期间的近期缓存。暂停区间在持久历史显示缺口；查询如果返回尚在内存的该区间，标记source=memory、persisted=false。服务重启读取enabled，继续已成功保存的暂停选择。
- **clear**：二次确认文字为“清空已保存历史和近期曲线”；保留账号、设备、当前实时值及当前enabled。协调器暂时隔离历史入口，阻止发布旧查询，丢弃尚未提交的旧聚合/队列；在一个短事务内递增epoch并写clearedAt，使旧segment的历史立即逻辑不可见；旧行/无引用维表随后按有界批次回收。不得为清空256MiB历史执行突破1MiB事务增长/WAL预算的大删除事务。提交成功后切换到新epoch的空近期缓冲和空聚合桶、新建segment，再恢复入口并返回成功。旧epoch批次不得重新入库或发布；旧查询返回409 historyChanged，历史游标也绑定epoch。
- clear开始时取消历史查询；事务切换中的新历史请求返回503 historyResetting。清空边界到提交期间的历史样本不回填，明示短暂gap；实时最新值持续更新。clear后仅将边界后的新观测放入近期历史，保留的当前传感器旧值不能重新入环形缓冲。跨越清空/恢复边界的首个差分区间不写历史，不把清空前累计量带回来。客户端收到新epoch的recordingStatus时取消旧请求、清空旧曲线，再拉取；迟到旧epoch响应丢弃。
- clear事务失败回滚并报告失败，旧epoch继续有效，不宣称已清空；放弃的未提交批次形成明确gap。崩溃恢复以已提交HistoryControl为准；内存本来不跨重启保留。paused时clear不自动恢复记录。删除为逻辑清空；尚待回收的旧epoch占用仍计入256MiB预算，必要时先清理再恢复持久写入，界面显示回收中和实际磁盘量。不承诺立即缩小文件、安全擦除介质或同步删除用户自行导出的备份；不自动VACUUM。

验收必须让clear与采样、排队提交、正在执行的查询、重试和重启交错，确认旧数据不会在成功清空后重新出现。
